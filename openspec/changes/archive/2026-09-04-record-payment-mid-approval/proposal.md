## Why

Some companies' real process pays as soon as the document reaches finance's step in the chain, not after every downstream signature clears. Today `PaymentService.record()` refuses any document that isn't `COMPLETED`, so finance's real, already-executed transfer can only be attached as evidence (`payment_attachment`) mid-flow — the formal payment record, budget settlement, and GL posting all wait for a second manual "round" once the last approver signs off, even though the money already left the company at step 4 of 7. That second round is pure paperwork friction with no financial control benefit, and worse, the system currently has no way to represent what should happen if a downstream step rejects a document whose money is already gone — `Auto-Release on Reject or Cancel` (`budget-control`) assumes the reservation can simply be given back, which is only true for money still in the budget.

## What Changes

- Allow `PaymentService.record()` to run against a document that is still `IN_APPROVAL`, when the document's **current** approval step has `requires_payment_slip = true` and the `payment_attachment` evidence that already unlocks that step's approval exists. Recording still only creates the `payment` row (rate, method, reference, evidence, FX) exactly as it does today, and still writes no `budget_txn` — that part of `Record Payment and FX Gain/Loss` is unchanged. It also does **not** emit `payment.settled` yet when done early, because GL posting on that event reads the `budget_txn` ACTUAL rows a `CUT_BUDGET` settlement produces, and those still only exist once the document is fully approved (`Payment-Ready Signal on Settlement`, unchanged, still fires only at `COMPLETED`). Steps before the gated step, or a gated step with no evidence yet, still cannot record — this is not a general "pay anytime" opening.
- When a document that already has an early-recorded payment later reaches `COMPLETED` normally, the existing `CUT_BUDGET` settlement fires exactly as today (RESERVE→ACTUAL) and the system emits `payment.settled` for the **already-existing** payment row instead of requiring a fresh one — closing what used to be a mandatory second manual visit to `ReadyToPayView`.
- Approval keeps running after an early record: later steps still APPROVE, REJECT, or RETURN exactly as configured today. Nothing about `requires_payment_slip`, `assertApprovable`, or the approve path changes.
- **BREAKING (behavioral):** a REJECT on a step downstream of an already-recorded payment still releases the full reservation exactly as `Auto-Release on Reject or Cancel` requires today — unconditionally, unchanged, because no ACTUAL was ever booked early. What's new: because a `payment` row already exists showing real money left the company for this specific submission, the document cannot simply be revised and resubmitted as if nothing happened. The payment is flagged as awaiting recovery, and resubmission is blocked until accounting resolves it. This case cannot occur today (record only ever happens after every step has already approved, so a rejected document never has a payment row), so no existing document is affected.
- Add a place for accounting to see documents flagged this way, so they know to raise the existing manual reversal journal (`gl-journal`, "Any Entry Can Be Reversed, Once" / `GL_JV_POST`) to true up the books for a real cash outflow that the ledger otherwise shows as a clean, fully-released reservation. No new GL posting or auto-reversal logic is introduced — this only makes the existing manual remedy discoverable for a case that previously couldn't exist.

## Capabilities

### New Capabilities
- `payment-recovery`: tracks documents whose payment was recorded before the document finished approval and were subsequently rejected by a later step, so the amount already paid out is never silently forgotten and accounting has a queue driving them to the existing GL reversal-journal flow.

### Modified Capabilities
- `payment-handoff`: `Record Payment and FX Gain/Loss` preconditions extend — a document also qualifies while `IN_APPROVAL` if its current step both requires and already has payment evidence attached (in addition to today's "fully approved and unpaid" precondition, which is unchanged); `payment.settled` emission is deferred to full-approval settlement for a payment recorded this way, reusing the existing row instead of creating a new one. `Ready-to-Pay Queue` is unaffected — an `IN_APPROVAL` document is never listed there regardless of an early payment, since the queue's job is unpaid obligations, not payment status.
- `approval-workflow`: `Reject Returns and Releases` gains a documented exception to "allow the requester to revise and resubmit" — REJECT continues to release the full reservation unconditionally exactly as today (invariant 5 is not touched), but when a `payment` row already exists for the document being rejected, the document additionally routes into `payment-recovery` and resubmission is refused until that is resolved.

## Impact

- `back/src/modules/payment-handoff/payment.service.ts` — relax the `doc.status !== DocStatus.COMPLETED` guard in `record()` to also accept the gated-mid-approval case; defer `payment.settled` emission until settlement for that case; on settlement, reuse an existing payment row for the document instead of requiring a new `record()` call.
- `back/src/modules/approval/approval-routing.service.ts` — the `REJECT` branch (`~line 309-318`) needs to check for an existing `Payment` row on the document and flag it for recovery; the resubmission path needs to refuse resubmission while a recovery flag is open.
- New: `payment.recovery_status` field, a query for "rejected with payment already recorded and unresolved," and a finance-facing list view (`front-end/src/views/payments/`) surfacing it — no changes to `gl-journal`'s posting or reversal logic, which is reused as-is.
- `front-end/src/views/documents/DocumentDetailView.vue` — surface the Record Payment action mid-flow when eligible (shared component with `ReadyToPayView.vue`), and surface the resubmit-blocked state when a document carries an unresolved recovery flag.
