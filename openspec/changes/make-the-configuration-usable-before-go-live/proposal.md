## Why

The software is ready for UAT. **The installed system is not usable**, and the blocker is
configuration, not code. Measured on the copy of the customer's database (2026-08-26):

| | |
|---|---|
| active `document_type` rows | 13 |
| **types anyone can actually raise** | **2** |
| `form_template` rows still `DRAFT` | 12 of 14 |
| `exchange_rate` rows | 0, while 7 documents are already in USD |
| **`approval_log` APPROVE rows written by a person** | **0** |

The eleven `REC*` disbursement types — the reason this system exists — are mapped to no department
at all, so nobody can raise one. The two that work, `BUDGET_PLAN` and `SPEND_HIST`, are import
artifacts. No document in this database has ever been approved by a human.

Nothing above is a defect. Each is a decision the customer has not yet recorded, and there is
currently no way to record one except by hand, one `INSERT` at a time, with no way to ask what is
still missing.

**This change builds the way to ask and the way to record. It does not invent the answers.** Which
department raises `RECWH`, who approves it, and above what amount a second signature is required
are the customer's to state; a script that guesses would put eleven wrong routes into production
faster than a person could put in one.

## What Changes

**A command answers "what is this environment still missing?"**
- `pnpm --filter back golive:check` reports, per company, every decision that stands between a
  migrated, loginable database and one people can raise documents in: an active type with no
  `dept_doc_type` mapping, a mapped template still `DRAFT`, a workflow whose steps name individual
  people rather than roles, a currency used by an existing document with no rate on file, an active
  type whose content lives elsewhere and names no screen.
- Read-only, and a separate command from the applier rather than a flag on it — for the same reason
  `permissions:check` is separate from `permissions:sync`: "what is missing" is worth being able to
  ask without changing the answer.
- **This is the deliverable that is useful today.** The customer has not supplied the mappings, so
  its output IS the question list to take to them.

**A command records the answers, idempotently.**
- `pnpm --filter back golive:apply <file>` reads a declarative config file and reconciles the
  database to it: `dept_doc_type` mappings, form-template publication, workflows and their steps,
  exchange rates, and `document_type.authoring_route`.
- Idempotent and re-runnable, like `seed:prod`: applying a file twice changes nothing the second
  time, so it can be run against staging, reviewed, then run against production.
- It SHALL refuse rather than default. A type the file does not mention is left alone and reported;
  a mapping naming a department or workflow that does not exist fails before writing anything.
- All-or-nothing per company, so a file with one bad line does not leave half a routing table.

**The config file is the artifact the customer fills in.**
- A template is generated by `golive:check --template`, pre-populated with every unconfigured type
  and blank slots for the decisions, so the customer edits a file rather than composing one.
- It is data, not code: reviewable in a pull request, diffable between environments, and the record
  of what was decided.

**`boot:check` gains the go-live check in reporting mode.**
- A deploy already fails on a type whose content lives elsewhere and names no screen. It does not
  fail on an unmapped type — a company mid-rollout legitimately has them — but it says how many
  there are, so "nobody can raise anything" is never silent.

## Capabilities

### New Capabilities

- `go-live-configuration`: the commands that report and reconcile the per-company configuration a
  migrated, loginable database needs before anyone can raise a document — document-type routing,
  form publication, approval chains, and rates.

### Modified Capabilities

- `platform-foundation`: *Local development environment*'s boot check additionally reports how many
  active document types cannot be raised, without failing on them.

## Impact

**Build-order capabilities touched:** none changes behaviour. This reads and writes the
configuration tables that `document-engine` (`document_type`, `form_template`, `dept_doc_type`),
`approval-workflow` (`workflow`, `workflow_step`) and `multi-currency` (`exchange_rate`) already
own, through their existing services wherever one exists.

**Invariants:** all hold, and two constrain the design. Invariant 1 (company isolation): the file is
scoped per company and a mapping crossing companies is refused, as `DeptDocTypeService.create`
already refuses one. Invariant 7 (configuration over code): this change exists *because* routing is
configuration — it adds a way to write that configuration, never a default for it. No ledger is
touched: `budget_txn` and `approval_log` are not written, read, or reachable from this path.

**Code**
- `back/scripts/golive-check.ts`, `back/scripts/golive-apply.ts`, plus the shared reader/validator
  they both use.
- `back/package.json` — two scripts, beside `permissions:check` / `permissions:sync`.
- `back/scripts/boot-check.ts` — the reporting-mode count.
- Existing services are called rather than bypassed: `DeptDocTypeService`, `FormTemplateService`,
  `WorkflowConfigService`, `ExchangeRateService`, `DocumentTypeService`.

**Data:** no migration. Every column this writes already exists and is already read.

**What this change cannot finish.** The decisions themselves. `golive:check` will keep reporting
eleven unmapped types until somebody states, per type: which department raises it, which workflow
approves it, and what that workflow's steps are. The current single workflow names two individuals
with no amount bands and is shared by every mapping; whether that is what the customer wants for
eleven disbursement types across nineteen departments is exactly the question this change is built
to put in front of them.

**Not in scope:** vendors and payee bank accounts (no active type sets `requires_vendor` or
`requires_payee`, so neither blocks go-live — an earlier assessment of mine wrongly listed them);
accounting periods (a date no declared period covers posts normally, and no active type posts a
journal); the fourteen screens whose search boxes filter nothing; and cleaning the `E2E-SBX`
sandbox out of a database before it is promoted.
