# UI run — the document lifecycle driven through the browser

**Date:** 2026-08-26
**Target:** front-end dev server on `:5173` (`/new/`), API on `:3000`, database `demo_erp`
**Driver:** Playwright MCP (a real browser, real clicks, real uploads)
**Result:** every lifecycle case passed. **4 UI defects found**, none of them in the approval or
budget engine — all four are in what the screens show or offer.

This complements `docs/e2e-run-2026-08-26.md`, which drove the same flows through the API.

---

## Before anything could be tested: the front-end could not reach the API

`front-end/.env` sets `VITE_API_URL = http://localhost:3000/api-new`, while this machine's
`back/.env` sets `PORT=5000`. The browser called 3000 and got `ERR_CONNECTION_REFUSED` on login —
nothing in the app was reachable. The run was done with the API moved to 3000.

**Correction to an earlier draft of this report,** which said the repository ships a combination
that cannot start. It does not. `back/.env.example` sets `PORT=3000`, both READMEs document 3000,
`main.ts` defaults to `process.env.PORT ?? 3000`, and `front-end/.env` expects 3000. Both `.env`
files are gitignored, so what diverges is one machine's local override, not the checked-in
configuration.

That makes it a smaller finding but not a non-finding: the symptom is a login screen reporting a
connection error, with nothing naming which of two files disagrees, and it cost the first part of
this session. A check that compares the two and says so belongs beside the other boot checks.

## Defect 1 — the approval inbox's search box does nothing

**Severity: medium. Reproduces every time.**

Typing anything into the search box on `/new/approvals` leaves the table exactly as it was.
Searching `SPEND` still returned twenty `REC*` rows.

`ApprovalInboxView.vue` binds the box to PrimeVue's client-side filter:

```vue
:filters="filters"
:globalFilterFields="['docNo', 'requesterName']"
```

but `AppDataTable` runs the table in **`lazy` mode**, where PrimeVue delegates filtering to the
server and never applies `filters` itself. Nothing handles the filter event, so the box is inert.

It matters because the inbox is paginated: this approver had **43 pending documents across 3 pages**,
and the only way to find one is to page through by eye.

`MyDocumentsView.vue` gets this right on the same components — it sends `docNo` to the server and
re-queries — so the fix has a working model in the same codebase. Note that even client-side
filtering would be wrong here: in lazy mode the client holds one page, so it would search 20 of 43.

## Defect 2 — a draft with its file attached is told the file is missing

**Severity: medium. Affects every draft of every `REC*` type.**

On any editable draft whose template has a required `file` field, the detail page shows a permanent
warning:

> This draft is missing required fields: ເອກະສານຕິດຂັດ. Fill them in before submitting.

The attachment is there — `document_attachment` had a row for every document in this run. The
banner's check builds its value map from `doc_field_value` alone:

```ts
for (const fv of docs.fieldValues as any[]) valuesByName[fv.fieldName] = fv.value || undefined;
...
.filter((f) => !valuesByName[f.fieldName])
```

A `file` field never has a `doc_field_value` row — its value is an attachment — so it is always
reported missing. The same applies to `line_items`, whose value is a `document_line`.

The server's own gate, which this is meant to mirror, special-cases exactly those two:

```ts
const present =
  f.fieldType === 'file'
    ? attachmentCount > 0
    : f.fieldType === 'line_items'
      ? lineCount > 0
      : val !== undefined && val !== null && val !== '';
```

The comment above the client version claims it "can never disagree with the wizard or the server
submit gate". It disagrees with both.

**Why it is worse than a stray warning.** When a submit is refused for a real reason, the true
message is a toast that disappears after a few seconds. The false banner does not. A requester who
looks away for ten seconds is left with one instruction on screen — attach the file you already
attached — and no trace of the actual reason. That is what happened on the over-budget case here.

## Defect 3 — the wizard offers a budget plan it cannot finish

**Severity: medium. A configuration gap against a requirement that already exists.**

`ແຜນງົບປະມານ` (`BUDGET_PLAN`) appears in the create wizard's type picker. Choosing it gives an empty
Details step, an optional line-items step, and a Save button. Submitting produces:

> This document moves budget but carries no budget movement; it cannot be approved as it stands

The draft is real — `BUDGET_PLAN-HAL-2026-0096` — and permanently unsubmittable: its content lives
on `budget_movement`, which the generic form cannot write. A document number is spent each attempt.
The only path that works is the budgets screen (`POST /budgets/plans`), which the earlier API run
exercised successfully.

The mechanism to prevent this is already built and already specified. `document-engine`'s
*A Document Type Declares Where Its Content Is Authored* says:

> Some types keep their content outside `document_line` and `doc_field_value`, where the generic
> form cannot reach it: **a budget plan**, adjustment and transfer carry `budget_movement` rows …
> A generic form offered for such a type produces a document that is well-formed and empty.

…and `CreateDocumentView.vue` already redirects when a type carries an `authoring_route`. This
company's `BUDGET_PLAN` row simply has `authoring_route` **NULL**, so nothing redirects.

The submit gate does catch it before the document reaches an approver — better than the worst case
the spec describes — but the user is still walked four steps into a dead end.

## Defect 4 — the budget picker asks a question the requester cannot answer

**Severity: high for daily use. Every budget-controlled line, every requester.**

The line-items step asks for a budget through a single flat dropdown. In this company's largest
department, `ພະແນກ ບໍລິຫານ`, that dropdown holds **92 options**, each labelled `code — name`:

```
1.101 — ອຸປະກອນເຄື່ອງໃຊ້ ຫ້ອງການ
1.102 — ອຸປະກອນ ເຄື່ອງອານາໄມ
...
1.111 — ງົບເດີນທາງ ພນ ບໍລິຫານ
1.112 — ງົບເດີນທາງ ພນ ບຸກຄະລາກອນ
1.113 — ງົບເດີນທາງ ພນ ມາດຕະຖານ
1.114 — ງົບເດີນທາງ ພນ ການຕະຫຼາດ
1.115 — ງົບເດີນທາງ ພນ ສົ່ງເສິມ
1.116 — ງົບເດີນທາງ ພນ ບໍລິການ
```

Six consecutive entries differing only in the last word, in a list of ninety-two, sorted by a code
the requester is expected to already know. There is nothing on screen that says what any of them is
for beyond its own name, and nothing that distinguishes the six travel budgets from one another
except a department name the requester may not be able to map to their own request.

**The grouping that would fix it already exists in the data and is thrown away.** Those six
budgets all hang off one parent node — `1.11 ເງິນເດີນທາງ ໄປວຽກຕ່າງແຂວງ` (travel to the provinces) —
and the 92 budgets fall into roughly thirteen such categories of three to ten each:

| Parent | Name | Children |
|---|---|---|
| `1.1` | ຄ່າບໍລິຫານ ທົວໄປ | 7 |
| `1.11` | ເງິນເດີນທາງ ໄປວຽກຕ່າງແຂວງ | 9 |
| `1.12` | ງົບເດີນທາງ ສູນຄັດແຍກ | 3 |
| `1.2` | ຈ່າຍ (ປະຈຳປີ ໃບອະນຸຍາດຕ່າງໆ) | 10 |
| `1.21` | ຄ່າລາຍຈ່າຍສາຂາຫຼັກ | 9 |
| `1.22` | ເງິນເດືອນ ພະນັກງານ ສາຂາຫຼັກ | 3 |
| `1.3` | ຄ່າງວດລົດ | 5 |
| `1.31` | ລາຍຈ່າຍສາຂາ ຕົວແທນ | 7 |

`GET /budgets/selectable` already returns `parentId` for every budget — the requirement
*Selectable Budgets for Document Creation* mandates it — and `LineItemsEditor` never reads it:

```ts
const budgetOptions = computed(() =>
  props.budgets.map((b) => ({ id: b.id, label: budgetLabel(b) })),
);
```

**But `parentId` as returned cannot be used.** The parents are *category* nodes that hold no money,
so they are never themselves selectable budgets and never appear in the response. Of the 92 budgets
in `ພະແນກ ບໍລິຫານ`, **85 have a parent the client has no way to name** — it holds an id that
resolves to nothing in the payload it was given. The one field that could organise the list is
present, unusable, and unused.

Two smaller things compound it:

- The dropdown's search box has no placeholder (visible in the screenshot as an empty box beside a
  magnifier), so the one affordance that makes 92 options tractable is undiscoverable. The filter
  itself does work — it is a PrimeVue `Select` with `filter`, unlike the inbox's inert one.
- Nothing indicates which budget a line *should* charge. The requester is asked to make an
  accounting decision with the accounting context removed.

**What this defect is not.** It is not "show the remaining balance in the picker". `budget-control`'s
*Selectable Budgets for Document Creation* deliberately gates this read on `DOC_CREATE` rather than
`BUDGET_VIEW` and states it "SHALL NOT return `amount_total`, any derived balance, breakdown
component, or ledger row". A requester who cannot read budget figures must still be able to pick a
budget. The fix has to work inside that rule — and grouping by category does, because a category
name is not a financial figure.
