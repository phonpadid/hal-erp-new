# End-to-end run — every document type, every ending

**Date:** 2026-08-26
**Target:** `demo_erp` (a copy of the production database), company `HAL` — HALLogistic
**Harness:** `back/e2e/` (Playwright, 83 checks), against the running API on `:5000`
**Result:** 69 passed, 14 failed — **3 distinct defects**, all in the seam between submitting a
document and routing it.

Nothing was rolled back. The sandbox department `E2E-SBX` holds every document the run raised, and
the failures are inspectable in place.

---

## What was exercised

The company has thirteen active document types. Each was driven through the four ways a document
can end:

| Ending | What it must do |
|---|---|
| approve → approve → `COMPLETED` | `RESERVE` at submit becomes `ACTUAL` at approval |
| approve → reject | the hold comes back as `RELEASE` |
| withdraw (by its author) | the hold comes back as `RELEASE` |
| return → resubmit → `COMPLETED` | the hold comes back, then is taken again |

On top of that: the approval rules (self-approval, eligibility, terminal states, who may withdraw),
the workflow shapes (amount bands, `PARALLEL_ALL`, `PARALLEL_ANY`, delegation), the two concurrency
locks (document numbering, budget reservation), and the reads a participant depends on (inbox,
detail, PDF, attachments, list filters).

### The database could not run these flows as it stood

The copied database maps only `BUDGET_PLAN` and `SPEND_HIST` to any department. The eleven `REC*`
types have form templates but **no `dept_doc_type` row anywhere**, so a document of those types
could not be raised at all. The suite therefore builds its own sandbox through the public API —
department, three accounts, a two-step workflow, a mapping per type, and one budget per type put in
force by drafting it, raising a real `BUDGET_PLAN` and approving it — and leaves every real
department's configuration untouched.

---

## What works

- **The budget arithmetic is correct everywhere.** Every ledger reconciles:
  `available = amount_total − Σ RESERVE + Σ RELEASE`, with `ACTUAL` reported but never subtracted.
  `RESERVE` and `ACTUAL` land as a pair on completion with no spurious zero-amount `RELEASE`;
  reject, withdraw and return each release exactly the outstanding hold and nothing more.
- **Several lines on one budget reserve their sum, once** — one `budget_txn` row per budget, not
  per line.
- **The control point blocks at its ceiling and not before it.** A budget of 1,000,000 accepted a
  1,000,000 document and refused 1,000,001 and, once full, refused 1. Withdrawing the first gave the
  whole ceiling back.
- **Both concurrency locks hold.** Eight simultaneous creates produced eight distinct document
  numbers. Two 600,000 submissions racing for a 1,000,000 budget produced exactly one `RESERVE` and
  one `BUDGET_EXCEEDED`; the loser stayed `DRAFT` with no ledger row. Two identical approvals posted
  at once counted once.
- **No self-approval, through delegation or around it.** The author of a document cannot approve it
  even when the step names them, and a delegation that hands the document to its own author does not
  make them eligible.
- **Refusals leave nothing behind.** A missing required field, a line with no budget, a currency
  with no rate, and an over-budget submission each left the document `DRAFT` with no hold taken.
- **`BUDGET_PLAN` does its job.** Approval flips its budgets to `ACTIVE` and mints their control
  points; rejection marks them `REJECTED` and frees the slot; a plan document with no
  `budget_movement` rows is refused at submit; an already-`ACTIVE` budget cannot be proposed again.

## Defect 1 — a returned document can never be sent again

**Severity: high. Reproduces on every one of the thirteen document types.**

Return a document (it goes back to `DRAFT`, holds released), fix it, submit it again — and it stays
`SUBMITTED` forever. It holds its budget, it is in nobody's queue, and no approver will ever see it.

`DocumentRouteService.materialise()` marks the previous attempt's `document_approval_step` rows
superseded and creates the replacement rows in one unit of work. MikroORM commits creates before
updates, so the INSERT reaches Postgres while the old rows are still live:

```
insert into "document_approval_step" (…) values ('a0dc27a9-…', '5ff805d4-…', 1, 'E2E step 1', …)
rollback
UniqueConstraintViolationException: duplicate key value violates unique constraint
  "document_approval_step_live_uniq"
detail: Key (document_id, step_no)=(5ff805d4-…, 1) already exists.
```

The whole routing transaction rolls back. The document keeps its `RESERVE`.

**Evidence in the database.** After three runs, 37 documents in `E2E-SBX` sit in `SUBMITTED`,
holding **51,000,000 LAK** of budget between them — `REC-HAL-2026-0008`, `RECADMIN-HAL-2026-0004`,
`RECWH-HAL-2026-0004`, `SPEND_HIST-HAL-2026-1191` among them. Replaying
`POST /documents/:id/start` by hand against any of them reproduces the 500 above. Every run adds
more, so re-count rather than trusting the figure:

```sql
with dept as (select id from department where dept_code = 'E2E-SBX')
select count(*) filter (where d.status = 'SUBMITTED')                        as stranded,
       sum(case t.txn_type when 'RESERVE' then t.amount
                           when 'RELEASE' then -t.amount
                           when 'ACTUAL'  then -t.amount else 0 end)         as budget_held
from document d
join budget_txn t on t.document_id = d.id
where d.department_id = (select id from dept) and d.status = 'SUBMITTED';
```

A stranded document carries two `RESERVE` rows and one `RELEASE`: the first submit reserved, the
return released, and the resubmit reserved again before its routing failed. The second reservation
is the one nothing will ever give back.

**Why nobody noticed:** `ApprovalSubmittedListener` logs everything except the "no applicable steps"
case at `debug`, a level the application does not enable. Every stranded document produced no log
line at all.

**Failing checks:** the twelve named `… returned, then resubmitted, still reaches COMPLETED`.

## Defect 2 — a withdrawal made before routing starts is undone

**Severity: high.**

Routing starts from the `document.submitted` event, after the submit transaction commits. In the
window before the route opens, the document is `SUBMITTED` — and `POST /documents/:id/cancel`
accepts a withdrawal there, as it should. But neither `cancel()` nor `start()` locks the document
row, so both read `SUBMITTED`, `cancel()` commits `CANCELLED`, and `start()` then writes
`IN_APPROVAL` over it.

The result contradicts itself:

```
 doc_no             | status      | approval_log        | budget_txn
 REC-HAL-2026-0004  | IN_APPROVAL | step 0: CANCEL      | RESERVE 1,500,000 + RELEASE 1,500,000
```

A request its author withdrew is back in an approver's queue, holding nothing. Approving it would
fail at settlement (`Actual … exceeds outstanding reserved 0`), so it cannot move forward either.

**Evidence:** `REC-HAL-2026-0004`, `REC-HAL-2026-0017`, `REC-HAL-2026-0070`, and one more from the
third run — four in all.

`act()` already takes `LockMode.PESSIMISTIC_WRITE` on the document row for exactly this reason;
`cancel()` and `start()` do not.

**Failing check:** `withdrawing between submit and routing must not be undone by the router`.

## Defect 3 — a workflow whose lowest step has an amount band refuses every first submission

**Severity: high for any company that configures banded approval. This one does not — yet.**

A workflow whose only step engages at or above 10,000,000 refused a **20,000,000** document:

```
POST /documents/{id}/submit → 400
"No approval step applies to this document, so nobody would ever be able to act on it.
 Check the workflow's amount bands and step conditions."
```

The routability gate on the submit path resolves applicable steps from
`document.budget_base_total_amount` — a column `submit()` stamps *later in the same method*, inside
its write transaction. On a first submission the column is null, so the gate compares every band
against `0` and finds nothing applicable, whatever the document is worth.

Two consequences:

- a workflow's lowest band must start at zero or the workflow is unusable — which is exactly the
  advice the auto-start listener's error message gives, so the advice is a symptom, not a rule;
- on a resubmission the gate reads the **previous** attempt's figure, so a document whose lines
  changed can be judged on an amount it no longer carries.

The step resolver itself is correct: the same workflow routes the same document properly once
`start()` runs, because by then the amounts are stamped. The gate and the router use one resolver
and disagree only because they hand it different input — which the spec (`Auto-Start Routing on
Submit`) already forbids in as many words.

**Failing check:** `a document that engages no step at all is refused at submit, holding nothing` —
its first half (a small document refused) passes; its second half (a large document routed) is where
it fails.

## Not covered by this run

- **SLA and escalation** — needs elapsed time, not reachable in a single run.
- **Quota-controlled types** — this company configures none (`requires_quota` is false on all
  thirteen).
- **Stock, journal-voucher and HR post-actions** — no active document type carries
  `ISSUE_STOCK`, `ADJUST_STOCK`, `TRANSFER_STOCK`, `POST_JOURNAL`, `UPDATE_EMPLOYEE` or
  `TERMINATE_EMPLOYEE`.
- **Budget `TRANSFER` and `ADJUST_*` documents** — no active document type carries those post
  actions either, so they can only be reached through `/budgets/transfer` and `/budgets/adjust`,
  which this run did not exercise.
- **Foreign-currency documents** — `exchange_rate` is empty, so a USD document is correctly refused
  at submit. The locked-FX path could not be reached; that refusal is asserted instead.

## Reproducing

```bash
cd back
# MinIO must be up: the REC templates all carry a required `file` field.
E2E_BASE_URL=http://localhost:5000 pnpm exec playwright test
```

The suite provisions idempotently, so it can be re-run. It only ever creates, and it creates only
inside `E2E-SBX`. It is not safe to point at production.

The proposed fixes are in `openspec/changes/keep-a-document-moving-after-submit/`.
